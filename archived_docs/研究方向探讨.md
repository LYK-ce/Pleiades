# Pleiades 研究方向探讨

基于 Pleiades 当前的系统架构（libp2p P2P 网络 + candle GGUF 推理引擎 + 流水线并行），探讨三个可能的研究方向。

---

## 方向一：异构设备最优模型分配策略

### 问题描述

当前 Pleiades 对模型层采用均分策略（total_layers / total_devices），未考虑设备间的算力、内存、网络带宽差异。在异构环境下（如 GPU 4090 + CPU i5 + GPU 3060 混合），均分会导致弱设备成为流水线瓶颈（木桶效应），强设备大量空闲等待。

### 研究内容

将模型分配问题形式化为优化问题：决策变量是每个设备分配的层范围，目标函数是最小化流水线最慢阶段的时间（$\min \max_i (T_{compute}^i + T_{transfer}^i)$），约束条件包括每个设备的可用内存和设备间的网络带宽。研究需要解决的子问题包括：(1) 设备算力 Profiling——度量每个设备每层 forward pass 耗时、可用显存/内存；(2) 层级粒度的计算量建模——Attention 层与 FFN 层的 FLOPs 差异显著，不能假设每层等价；(3) 分配算法——动态规划或启发式搜索找到最优分割点；(4) 在线自适应调整——当网络波动或设备负载变化时，能否在运行时动态调整分配方案。

### 相关工作

PipeEdge（2022）研究了边缘 pipeline 并行的层分配问题，HetPipe（2020）针对异构 GPU 集群提出了 wave 调度算法，Petals（2023）在去中心化场景做了初步尝试。但已有工作大多假设数据中心或固定拓扑，**边缘异构设备 + 动态 P2P 拓扑**的组合是差异化点。

### 评估

- 学术价值：中高
- 实现难度：中——算法层面不太复杂，集成到 Control 层的分配逻辑中替换均分即可
- 建议定位：**近期目标**，可快速出成果

## 方向二：容错与动态设备管理

### 问题描述

当前 Pleiades 的流水线推理中，任何一个设备掉线（断电、网络中断、进程崩溃）都会导致整条 pipeline 断裂、推理失败，且无法恢复。在边缘场景下设备不可靠性远高于数据中心，这一问题尤为突出。

### 研究内容

需要解决四个子场景：

1. **设备中途崩溃**：pipeline 断裂，该设备上的 KV cache 丢失。解决思路是 Checkpoint 机制——定期保存中间激活值到临近设备，检测到掉线后将该设备的层迁移到备选设备，从最近的 checkpoint 恢复推理。关键挑战是 KV cache 状态的保存与恢复代价。

2. **设备主动离开**：设备希望优雅退出。解决思路是预通知协议——离线前通知协调者，在当前请求完成后触发动态重分配，将该设备的层 split 并迁移到剩余设备。

3. **新设备加入**：如何利用新增算力。解决思路是热加入——在两次推理之间的空闲期重新 balance 层分配，利用 DHT 发现新设备并自动纳入 pipeline。

4. **网络波动**：某段链路延迟突增。解决思路是自适应超时与备选路径——检测到延迟增大时，尝试通过其他设备中继，或动态调整该段的层分配以减少传输量。

核心技术挑战在于 KV cache 一致性（自回归生成中每个设备维护自身的 cache 状态）、检测延迟与恢复成本的权衡（心跳频率越高检测越快但开销越大），以及对用户的透明性（理想情况是设备故障后推理短暂停顿但不中断）。

### 相关工作

Petals 实现了基本的 relay 备选路径机制，但仍依赖中心化的健康检查。SpotServe（2024）研究了 spot instance 场景下的容错推理，但针对云端而非边缘。**边缘设备端到端容错方案**仍是开放问题。

### 评估

- 学术价值：高——分布式推理的核心痛点
- 实现难度：高——涉及状态管理、一致性协议等分布式系统核心问题
- 建议定位：**中期目标**，解决实际痛点

## 方向三：P2P 网络与分布式推理的深度结合

### 问题描述

当前 Pleiades 对 libp2p 的使用仅限于节点发现（mDNS）和数据传输（request-response + stream），P2P 网络的核心能力（DHT、gossip、去中心化协调）远未充分利用。现有的推理协调仍是传统的 master-slave 模式（由发起者中心化分发模型、编排 pipeline），这在可扩展性和鲁棒性上存在瓶颈。

### 研究内容

**1. 去中心化模型分发（DHT + Content Addressing）**

模型的每个层片段用内容哈希标识，注册到 Kademlia DHT。当后续设备需要同一模型的某些层时，通过 DHT 发现网络中已持有这些层的设备，直接 P2P 拉取（类似 BitTorrent 的 swarming 下载），协调者无需重复切分和发送。这解决了当前协调者带宽瓶颈的问题，尤其在多设备同时上线时效果显著。

**2. 无中心协调的推理（全去中心化）**

设计去中心化推理协议：每个设备在 DHT 中 publish 自己持有的模型层范围和当前算力/负载信息；任意设备发起推理请求时，通过 DHT 查询自组织发现一条完整的 pipeline；推理请求沿 pipeline 自动流转（fire-and-forget），无需单一协调者控制全过程。这使系统真正去中心化——没有 master/slave 之分，任何设备既是推理发起者也是计算参与者。

**3. Gossip-based 负载感知调度**

设备通过 gossip 协议周期性广播自身负载信息（GPU/CPU 利用率、内存剩余、推理队列深度）。新推理任务根据全网负载状态自动路由到最空闲的 pipeline。相比中心化调度，gossip 方案更可扩展（O(log N) 收敛）且无单点故障。

**4. 激励机制**

借鉴 BitTorrent 的 tit-for-tat 和区块链的信誉系统：贡献算力的设备获得"推理积分"，请求推理时消耗积分。不贡献的设备被降低调度优先级。可以用轻量级本地记账（无需真正的区块链），通过 gossip 在节点间同步信任分数。

### 相关工作

Petals（2023）是最接近的相关工作，实现了去中心化的 LLM 服务，但仍依赖中心化的 coordinator 和 reputation server。BitTorrent、IPFS 等 P2P 文件共享系统提供了成熟的去中心化协议范式。**将 P2P 网络协议与 LLM 推理优化深度结合**是目前文献中几乎没有深入探讨的方向。

### 评估

- 学术价值：最高——"去中心化 LLM 推理"概念本身就具有很强的故事性和新颖性
- 实现难度：高，但可渐进式推进（先做 DHT 模型分发 → 再做去中心化协调 → 最后做激励机制）
- 建议定位：**核心创新点**，最有论文价值，也是 Pleiades 区别于其他分布式推理系统的根本差异

---

## 总体建议

| 方向 | 学术价值 | 实现难度 | 时间线 |
|------|---------|---------|--------|
| 最优分配策略 | ⭐⭐⭐ | ⭐⭐ | 近期 |
| 容错与动态管理 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 中期 |
| P2P 深度结合 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 核心 |

三个方向并不互斥，建议递进式推进：先实现最优分配策略使系统基本可用，再引入容错机制提高鲁棒性，在此基础上逐步将中心化协调替换为 P2P 去中心化协议，最终形成完整的"去中心化边缘 LLM 推理"方案。
