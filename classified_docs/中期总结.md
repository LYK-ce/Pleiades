## 一、项目概述

**Pleiades** 是一个面向**边缘设备的分布式大语言模型（LLM）推理运行时框架**，使用 **Rust** 编写。其核心目标是让多台边缘设备（如笔记本、嵌入式 GPU 设备等）通过 P2P 网络协同完成大模型的流水线推理，无需依赖中心化服务器。

### 核心理念

- **去中心化**：基于 libp2p 的 P2P 网络，节点自动发现、自主协调
- **流水线并行**：将大模型按层切分，分配到多个节点，通过张量流（Tensor Stream）实现流水线推理
- **指令驱动**：两级指令架构（Orchestrator 级 TaskInstruction + ML Engine 级 Instruction），程序化/声明式的任务编排
- **纯 Rust 实现**：基于 `candle` ML 框架实现 GGUF 模型推理，兼顾性能与安全性

## 三、各组件详细说明

### 3.1 Orchestrator（编排器）

**核心中枢**，负责接收用户命令、调度 Job、管理生命周期。

| 子模块 | 职责 |
|--------|------|
| `core.rs` + `branch_*.rs` | 主事件循环（`select!`），4 个分支：用户命令、网络入站、流事件、Job 生命周期 |
| `compiler.rs` | 将用户意图编译为 `TaskProgram`（指令序列），支持 Run/Pipeline/Send/Receive 等多种 Job 类型 |
| `executor/mod.rs` | `JobExecutor`：异步执行 TaskProgram，支持取消和补偿 |
| `executor/task_engine.rs` | `TaskEngine`：指令解释器，维护 IP/SlotFile/ExecutionMode |
| `executor/handler_*.rs` | 各类指令处理器（Data/Inference/Network/Control/Scheduler/Pipeline） |
| `job.rs` | Job 数据契约：`JobId`, `JobKind`, `JobState`, `LifecycleEvent` |
| `instruction.rs` | `TaskInstruction` 枚举：定义所有 Orchestrator 级指令 |
| `slot.rs` | 槽位系统：`SlotId` / `SlotValue` / `SlotFile`，指令间数据传递媒介 |
| `command.rs` | `UserCommand` 枚举：用户可发出的命令（Run, Pipeline, Send, Quit 等） |
| `inference_id.rs` | 全局推理 ID 生成器（原子递增） |

**设计亮点**：
- 正向序列 + 补偿序列（`TaskProgram` = `forward` + `compensation`），超时/取消时自动清理资源
- IP 自增 + `JumpIf` 条件跳转实现控制流
- `SlotFile` 替代传统参数传递，指令间解耦

---

### 3.2 ML Engine（推理引擎）

**核心推理执行层**，提供 GGUF 模型加载、Qwen3 推理、寄存器架构的执行引擎。

| 子模块 | 职责 |
|--------|------|
| `ml_thread_engine.rs` | Session/Thread 引擎核心：`Session`（线程私有容器）、`Session_Handle`（通道句柄）、`Execute()`（指令执行器） |
| `ml_thread_engine_instruction.rs` | 寄存器架构指令集：Input/Encode/Decode/Inference/Sample/Send/Receive/Loop/BreakIf 等 |
| `ml_thread_register.rs` | 寄存器系统：TEXT(4) / TOKENID(4) / TENSOR(4) / FLAG(4) / META(8) |
| `gguf_model.rs` | GGUF 模型加载/推理/编解码接口 |
| `gguf_model_manager.rs` | 模型分析（层结构）/ 按层加载 / 模型切分 |
| `gguf_tensor.rs` | 张量序列化/反序列化（网络传输用） |
| `GGUF_Models/qwen3.rs` | Qwen3 模型具体实现（Attention + MLP + RoPE） |
| `capability.rs` | `ML_Engine_Capability` trait：对 Orchestrator 暴露的统一接口 |
| `service.rs` | `ML_Engine_Service`：持有 Storage + Session 注册表的服务实现 |

**设计亮点**：
- **寄存器架构**：所有数据通过 TEXT/TOKENID/TENSOR/FLAG/META 寄存器传递，指令无隐式状态
- **独占线程**：每个 Session 独占一个 OS 线程，避免阻塞 tokio runtime
- **三种推理模式**：单机（Run）、协调者（Coordinator，首尾层 + 采样）、中继（Relay，中间层）
- **支持 CUDA**：通过 candle feature flag 可选 GPU 加速

---

### 3.3 Network（P2P 网络层）

**基于 libp2p 的去中心化网络通信**，支持多种传输模式。

| 子模块 | 职责 |
|--------|------|
| `network_service.rs` | `Network_Service`：libp2p Swarm 事件循环 |
| `node_handle.rs` | `NodeHandle`：通过命令通道与 Swarm 通信 |
| `capability.rs` | `Network_Capability` trait：统一接口（请求-响应、文件流、张量流、DHT） |
| `data_protocol.rs` | 请求-响应协议（DataType 命令/数据/文件通知） |
| `stream_protocol.rs` | 文件流协议（header 协商 + raw data 传输） |
| `tensor_stream_protocol.rs` | 张量流协议（持久化 stream，帧头 + offset + eof 标记） |
| `inbound_manager.rs` | 入站请求路由管理 |
| `outbound_manager.rs` | 出站响应路由管理 |

**传输协议设计**：
- **Request-Response**：用于短消息（命令分发、Pipeline Join 请求、Establish 握手）
- **File Stream**：单次文件传输（模型分片分发），带 header 协商 + Accept/Reject 机制
- **Tensor Stream**：持久化流，用于推理过程中的张量帧连续传输，支持 EOF 标记

**网络发现**：mDNS（局域网自动发现） + Kademlia DHT（广域网路由）

---

### 3.4 Storage（存储管理）

**磁盘空间管理器**，提供文件级并发安全访问和配额管理。

| 功能 | 说明 |
|------|------|
| `StorageManager` | 核心管理器：文件注册、路径解析、配额追踪 |
| `ReadGuard` / `WriteGuard` | RAII 守卫：基于引用计数的并发读写保护 |
| `Reservation` | 空间预留机制：写入前预占配额，写入完成后确认 |
| `QuotaInfo` | 配额信息查询（total/used/reserved/available） |
| `ChecksumAlgorithm` | 文件校验算法支持 |

**设计亮点**：
- RAII 守卫自动管理锁生命周期
- 预留机制避免并发写入超出配额
- Arc 共享，多组件（ML Engine、Orchestrator、Network）无锁安全访问

---

### 3.5 LLM_IO（文本交互通道）

**前端与 ML Session 之间的双向文本通道**。

- `LLM_IO_Broker`：管理通道分配/回收，支持按 JobId 索引
- `IoFrontend`：前端侧端点（发 Prompt，收 Completion）
- `IoHandle`：ML 侧端点（收 Prompt，发 Completion）
- 生命周期：`Allocate → Take_Frontend + Take_ML_Side → 交互 → Deallocate`

---

### 3.6 Tensor_IO（张量流管理）

**张量流的热切换与广播管理**。

| 功能 | 说明 |
|------|------|
| `Tensor_Port_Switch` | 全局 Switch：注册/注销/热切换管理 |
| `Tensor_IO_Endpoint` | ML Session 持有的 I/O 端点（Send/Receive） |
| 热切换 | Core 可随时 `Swap_Input` / `Set_Outputs`，ML Thread 无感知 |
| 广播 | Outbound 支持多目标，一次 Send 写入所有下游节点 |
| 故障上报 | 单目标失败不中断推理，通过 channel 异步通知 Core |

---

### 3.7 Scheduler（拓扑调度器）

**分布式流水线拓扑规划**。

- `Scheduler_Capability` trait：纯函数接口，输入模型信息 + 节点列表 → 输出 `Pipeline_Plan`
- `Pipeline_Plan`：Coordinator 层范围 + 出站目标 + Worker 列表（每个 Worker 含层范围/目标/设备）
- 当前实现：均匀分配策略（按节点数等分模型层）

---

### 3.8 PeerManagement（节点管理）

**节点信息的并发安全管理**。

- `PeerManager`：核心组件（RwLock 保护的 HashMap）
- `PeerInfo`：节点完整信息（ID、地址、状态、能力、带宽、心跳）
- `PeerStatus`：Connected / Disconnected / Idle / Busy
- `PeerCapability`：节点计算能力描述
- `PeerHandle`：外部调用接口（impl `Peer_Management_Capability`）

---

### 3.9 EventBus（全局事件总线）

**系统内部的异步事件广播**。

- 基于 `tokio::sync::broadcast` 实现多生产者多消费者
- `Bus_Event`：日志、网络状态、Job 状态等通知型事件
- TUI 通过订阅 EventBus 实时展示系统状态

## 四、关键技术优势

### 4.1 架构优势

| 优势 | 说明 |
|------|------|
| **去中心化** | 无需中心服务器，P2P 网络自动发现节点，任何节点都可发起推理 |
| **纯 Rust** | 内存安全、高性能、零成本抽象，无 GC 开销 |
| **模块化 Capability trait** | 每个模块通过 trait 暴露能力，测试时可轻松 mock（Stub），降低耦合 |
| **两级指令架构** | Orchestrator 级编排 + ML Engine 级执行，关注点分离，灵活组合不同推理模式 |
| **Pipeline 并行** | 模型按层切分，多节点流水线并行推理，突破单机显存限制 |

### 4.2 工程优势

| 优势 | 说明 |
|------|------|
| **正向 + 补偿序列** | Job 异常/取消时自动执行补偿（如 ShutdownSession），确保资源不泄漏 |
| **RAII + 引用计数** | Storage 守卫、CancellationToken 等利用 Rust 所有权机制自动清理 |
| **热切换** | Tensor_IO 支持运行时切换流目标，无需重启推理 Session |
| **独占线程 + 指令泵** | ML Session 独占线程避免阻塞异步运行时，每步可取消 |
| **candle + GGUF** | 原生 Rust 推理（无 Python 依赖），支持 CUDA GPU 加速 |

### 4.3 创新点

1. **寄存器架构的 ML 执行引擎**：类似 CPU 指令集设计，指令间通过寄存器传递数据，无隐式状态
2. **Slot 系统**：Orchestrator 指令间的数据媒介，支持原子值/文件句柄/Stream/IoHandle 等多种类型
3. **Compiler 模式**：将用户意图"编译"为指令序列，声明式 vs 命令式的平衡
4. **张量流广播 + 故障隔离**：单个下游节点故障不影响其他节点和推理持续

## 九、相关工作对比：Pleiades vs Parallax

### 9.1 Parallax 概述

[Parallax](https://github.com/GradientHQ/parallax) 是 Gradient 公司开发的分布式 LLM 推理引擎，以 Python 编写。其核心特性包括：

- **Pipeline Parallel Model Sharding**：将模型按层切分到多节点
- **中心化 Scheduler**：固定的调度服务器（FastAPI + Lattica P2P 库）
- **成熟推理后端**：SGLang（GPU）、vLLM（GPU）、MLX-LM（Mac）
- **两阶段调度**：Layer Allocation（DP/Greedy + Water-filling） + Request Routing（DP/Round-Robin）
- **支持大模型**：DeepSeek-V3、Qwen3-Next、Llama 3、GPT-OSS 等 100B+ 参数模型

### 9.2 架构对比

| 维度 | **Parallax** | **Pleiades** |
|------|-------------|-------------|
| 架构模式 | 中心化 Scheduler + 分布式 Workers | **完全去中心化**，角色运行时动态决定 |
| 调度节点 | 固定的 Scheduler Server 进程 | 每个节点运行相同代码，Coordinator 由运行时选举 |
| P2P 网络 | Lattica（自研 Python P2P 库） | libp2p（Rust 原生，mDNS + Kademlia DHT） |
| 调度策略 | DP + Water-filling + 动态 rebalance | 初版均匀分配；规划计算感知加权分配 |
| 推理后端 | SGLang / vLLM / MLX-LM（成熟 Python 框架） | 自研 Rust ML Engine（Candle + GGUF） |
| 编程语言 | Python（FastAPI + asyncio） | Rust（Tokio 异步运行时） |
| 目标场景 | 云 / GPU 集群 + Mac 设备混合推理 | **边缘设备集群**，无中央服务器、局域网自动发现 |
| 请求处理模型 | 预建管道 + 路由分发（服务化） | Per-request Job + TaskProgram 编排（Job 化） |
| 并发模型 | 多线程 + 共享状态 + 锁同步 | `tokio::select!` Actor 模型，无锁设计 |

### 9.3 调度系统对比

**Parallax 的两阶段调度（成熟度更高）**：
- Phase 1 — Layer Allocation：使用 DP 或 Greedy 算法，基于节点 TFLOPS/显存带宽，通过 water-filling 算法按计算能力比例分配层
- Phase 2 — Request Routing：对每个请求动态计算最小延迟路径（考虑 RTT + 节点负载）
- 支持 node join/leave 时增量重平衡、heartbeat 超时自动驱逐

**Pleiades 的调度（去中心化 + 可编程）**：
- `Plan_Pipeline()` 为纯函数：模型信息 + 可用节点 → 拓扑 plan
- 当前策略：均匀分层，余数给 Coordinator
- 拓扑为环形流水线：Coordinator → W1 → W2 → … → WK → Coordinator
- 每次 Job 独立编排，天然适应动态环境

### 9.4 核心设计哲学差异

**Parallax = 应用**：预定义的推理服务管道，请求流过即可。

**Pleiades = 操作系统**：可编程的执行平台，通过 TaskProgram 定义任意工作流。

| OS 概念 | Pleiades 对应 |
|---------|--------------|
| 进程 | Job（JobId, JobKind, JobState） |
| 地址空间 | SlotFile（隔离的键值内存） |
| 程序计数器 | `ip: usize`（指令指针） |
| 代码段 | TaskProgram（指令序列 + 补偿链） |
| ISA 指令 | TaskInstruction 枚举 |
| 系统调用 | Capabilities trait 接口 |
| 文件系统 | StorageManager |
| IPC/信号 | EventBus（Pub/Sub 广播） |
| GPU 微码 | ML Engine Instruction（寄存器架构） |
| 内核 | Orchestrator Core（select! 事件循环） |

### 9.5 Pleiades 的独特优势

#### 1. 真正的去中心化

Parallax 的 Scheduler Server 是**单点故障**。Pleiades 无需固定 Scheduler Server，任何节点宕机（包括当前 Coordinator）后系统可重新选举恢复。

#### 2. OS 级可编程性

Parallax 做的事情是固定的（不同模型走同样的管道）；Pleiades 能做的事情是**无限的**——通过编程定义任意工作流：

| 创新点 | Parallax 实现难度 | Pleiades 实现难度 | 原因 |
|--------|-----------------|-----------------|------|
| 投机解码 | 🔴 重写 Worker + Scheduler | 🟢 新 TaskProgram 编排 | 需要两模型交互 |
| MoE 专家路由 | 🔴 需新路由维度 | 🟢 新增指令 | 当前路由只支持线性层 |
| 跨节点 KV Cache 迁移 | 🔴 改 SGLang 内部 | 🟢 张量流传输 | Pleiades 控制张量流 |
| 长推理断点续存 | 🔴 无 checkpoint 机制 | 🟢 SlotFile 序列化 | TaskEngine 状态天然可序列化 |
| 条件退化（大→小模型） | 🟡 需改 Scheduler | 🟢 `JumpIf` 分支已有 | 程序内支持 |
| 联邦推理（多方隐私） | 🔴 架构不支持 | 🟢 新增加密指令 | 全栈自研可控 |
| Pipeline 内插入预/后处理 | 🔴 只能外部 | 🟢 在 TaskProgram 中编排 | 自然表达 |

#### 3. Rust 原生性能与安全

- 无 Python GIL 限制
- 编译器保证内存安全和无数据竞争
- 零拷贝张量流传输
- 适合资源受限的边缘设备

#### 4. Actor 模型并发（select! 四分支）

Pleiades 的 Core 使用 `tokio::select!` 实现无锁 Actor 模型：
- 天然串行：每轮只处理一个事件，无需锁
- 零死锁风险
- 事件因果确定，可调试、可重放
- 重活通过 `tokio::spawn` 委派，不阻塞核心循环

Parallax 使用多线程 + 共享状态：需要 `threading.Condition`、`threading.Event`、`queue.Queue` 等同步原语，存在锁竞争和死锁隐患。

#### 5. 自研推理栈的深度控制

Candle + GGUF 意味着完全掌控推理计算图，可以做 Parallax 做不到的事情：
- 自定义 tensor 编解码（张量流传输时）
- 跨节点 KV Cache 精确管理
- Batch Stealing（为系统 Agent 偷取推理 slot）
- 按需量化（不同节点不同精度）

### 9.6 Parallax 的优势（Pleiades 需追赶的部分）

| 维度 | 说明 |
|------|------|
| 成熟的调度算法 | DP + Water-filling + 动态 rebalance，Layer 级精确负载感知 |
| 生产级推理后端 | SGLang/vLLM 的 continuous batching、paged attention、CUDA 优化 |
| 大模型验证 | 已支持 DeepSeek-V3、Qwen3-Next 等 100B+ 参数模型 |
| 多路 pipeline | 通过 layer replication 形成多条并行 pipeline，支持高并发 |
| 吞吐量 | Continuous batching 使多请求共享 GPU forward pass |

### 9.7 定位差异总结

- **Parallax** = 面向 GPU 集群的**高性能推理服务**（中心化调度 + 成熟推理框架）
- **Pleiades** = 面向边缘设备的**自治推理运行时操作系统**（去中心化 + 自研可编程栈）

Pleiades 的护城河在于：**OS 级抽象带来的无限可编程性**——未来任何分布式推理领域的创新（投机解码、MoE、联邦推理、多模态 pipeline...），都可以在 Pleiades 上实现为"一组新指令 + 一个新 TaskProgram"，而不需要重新设计系统。

## 十、前瞻方向：Self-Hosting Agent（自驱动智能运行时）

### 10.1 概念

在 Pleiades 平台中嵌入一个 **LLM 驱动的系统 Agent**：
- 复用用户已加载的 LLM 模型
- 从用户推理中"偷"一个 batch slot（Batch Stealing）驱动 Agent 推理
- Agent 观察系统事件（EventBus），生成结构化决策，驱动平台的错误恢复、性能优化等自治行为

### 10.2 工作原理

```text
[EventBus 事件流]
  → Connection_Closed { peer: "Worker3" }
  → Job_State_Changed { job: 42, phase: "stalled" }

[System Agent 观察 + 推理]
  → 向已加载的 LLM 提交 system prompt + 事件上下文
  → LLM 输出结构化决策: {"action": "replan_pipeline", "exclude": "Worker3"}

[执行决策]
  → Agent 生成新 TaskInstruction 序列
  → Core 执行: Cancel Job 42 → Re-compile → Spawn new Pipeline Job
```

### 10.3 为什么在 Pleiades 上可行

| 前提条件 | Pleiades | Parallax |
|---------|----------|----------|
| 控制推理引擎内部调度 | ✅ 自研 ML Engine，能插入 system batch | ❌ SGLang/vLLM 是黑箱 |
| 可编程工作流 | ✅ Agent 是一个 TaskProgram | ❌ 无法在 pipeline 中插入自定义逻辑 |
| 结构化决策→执行 | ✅ LLM 输出 → 解析 → TaskInstruction → 执行 | ❌ 没有指令抽象层 |
| 事件观测能力 | ✅ EventBus 全系统事件可订阅 | ❌ 事件分散在各线程 |
| 低开销偷 batch | ✅ 控制 batch composition | ❌ batch 由 SGLang 内部管理 |

### 10.4 Agent 用例

1. **智能错误恢复**：Worker 掉线后，Agent 分析原因 → 决定重新规划 Pipeline 或通知用户
2. **性能自优化**：观察推理速度下降趋势 → 判断瓶颈节点 → 动态 rebalance
3. **自然语言设备管理**：用户说"只用两台笔记本，不用手机"→ Agent 解析意图 → 约束 Scheduler
4. **预测性维护**：观察节点 latency 异常模式 → 提前迁移任务到健康节点

### 10.5 学术价值

这是一个全新的研究方向：**Self-Aware Inference Runtime / LLM-in-the-Loop Systems**

- **Self-Hosting**：推理系统用自己服务的模型管理自身（reflexive system design）
- **Zero-Cost Governance**：Agent 与用户推理共享 forward pass，管控开销趋近于零
- **Emergent Behavior**：故障恢复策略不是硬编码的，而是从 LLM 通用推理能力中涌现的

## 十一、总结

Pleiades 项目在中期阶段已建立完整的系统架构骨架和核心模块实现。通过**指令驱动的两级执行引擎**、**Capability trait 的模块化设计**以及**基于 libp2p 的 P2P 网络**，实现了一个功能完备的分布式 LLM 推理运行时原型。单机推理已可端到端运行 Qwen3 模型，分布式 Pipeline 推理的编排框架已搭建完毕。

与 Parallax 等同类工作相比，Pleiades 的核心差异化在于：
1. **OS 级可编程性**：双层指令集 + Job 化执行，支持任意推理工作流编排
2. **真正去中心化**：无单点故障，适应边缘设备动态环境
3. **Rust 全栈自研**：从网络到推理引擎全部可控，为创新提供最大自由度
4. **Self-Hosting Agent 潜力**：为未来智能化自治运行时奠定基础

后续工作将聚焦于 Pipeline 端到端联调、智能调度策略与系统稳定性增强，并探索 Self-Hosting Agent 方向的原型实现。
